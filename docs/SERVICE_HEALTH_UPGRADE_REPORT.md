# Services health upgrade — 2026-09-25

Implemented in the existing dsmonitor application. Trace Explorer, Engine Trace Explorer, Service × Engine matrix, process monitoring, error monitoring and shared-state views are retained. No operational engine code, CRM schema, business record, workflow, approval or delivery was modified. No engine was started/restarted by this work. Validation used temporary local monitoring databases.

The important live finding is **insufficient evidence**, not a green dashboard: CRM authenticated reads work; Domain Merchant intelligence persistence is visible; subsequent shared-loop handoffs are not established by the available scoped records. Supabase answers but the independent monitor credential cannot SELECT organizations (42501). See `service-health-validation.json` for the exact observation time and evidence.

1. **Old algorithm.** `trace_service.overview` selected observed stages, prioritized failures/stalls, and converted COMPLETED plus a source timestamp into HEALTHY. It optionally applied an expected-activity interval. Engine availability was separate, but current permissions/connectivity were not prerequisites for a healthy matrix cell. That conversion has been removed. Historical counts, durations, source status and trace navigation remain.

2. **New algorithm.** The existing overview is enriched by `services/service_health.py`. Each relationship has connectivity, read, write, handoff, workflow and activity dimensions; source timestamps; verification timestamps; reasons; evidence; failed/latest trace links; and observed health transitions. Registry contracts describe inputs, outputs, dependencies, handoffs and optional activity expectations. Precedence is NOT_CONFIGURED for known nonparticipants; DISCONNECTED; unresolved FAILED; upstream NOT_REACHED; DEGRADED; IDLE; HEALTHY; otherwise UNKNOWN. Availability remains independent. UNKNOWN never silently recovers a failure.

3. **HEALTHY.** CONNECTED, every required read VERIFIED, write capability VERIFIED, no unresolved failure/cutoff/impairment/stall/missed schedule, and every registered relevant edge either confirmed or explicitly not expected. A pending/unknown edge prevents HEALTHY. A waiting workflow remains separately WAITING and is not promoted to a successful workflow. A generic endpoint HTTP 200, process, heartbeat, old stage completion or configured credential cannot alone satisfy this rule.

4. **IDLE.** The same current connectivity/read/write prerequisites, no unresolved impairment/failure/cutoff, and explicit evidence that work is not due: a configured schedule is between due times, or a fresh engine report says `work_expected:false`. Pending obligations prevent IDLE. Unknown handoff history can coexist with IDLE because no flow is currently due, but remains visibly UNKNOWN. An unknown schedule does not establish IDLE on its own.

5. **DEGRADED.** A required dependency/API/authentication observation is impaired, required read fails, write capability explicitly fails, a registered handoff fails or passes its configured pickup deadline without a receipt, an expected run misses its allowed grace, or an existing stage exceeds its opt-in stall threshold. Reasons identify the dimension and, for handoffs, the source ID, age and threshold. A late receipt diagnosis explicitly says the bounded context may omit consumption; it is not a fabricated assertion that no receiver ever ran. Monitor-only credential failures with unknown engine impact remain UNKNOWN and are labeled with their monitoring scope; they do not establish operational degradation.

6. **FAILED.** A retained workflow has an unresolved root failure attributed to this service and engine. A later unrelated success does not erase it. Existing trace projection resolves successful retries within a run; an explicitly linked successful child retry in the same organization can resolve its failed parent. This deliberately includes old unresolved source failures: age alone does not resolve them. The failed trace is linked. Generic undated log errors are not attributed to nearby workflows.

7. **DISCONNECTED.** A required dependency transport probe is unreachable/times out, or a fresh, organization-scoped engine report explicitly reports its dependency disconnected. Shared dependency checks identify the monitor's network vantage point; a fresh engine report is authoritative for its own vantage. HTTP permission/authentication errors are responses, not transport disconnection. Read/write show UNAVAILABLE when disconnected. The process can still be ONLINE.

8. **NOT_CONFIGURED.** A known registered service has neither an implemented engine contract, a registered stage/coordinator nor observed stage participation in that engine. No timestamp freshness test can produce this state. An observed implementation overrides a default absence. Unknown/unregistered participation stays UNKNOWN instead of inventing a nonimplementation claim. Registry notes explain partial and missing implementations.

9. **NOT_REACHED.** The latest relevant workflow has an explicit sequential upstream cutoff and the engine has no reached stage in that workflow. Existing Trace Explorer cutoff calculations are reused. Pipeline absence uses an explicit stage name, not engine name alone, because CRM and MMonolith occur repeatedly in the cycle. Downstream cells do not become FAILED merely because an upstream engine failed.

10. **UNKNOWN.** Any other insufficient or contradictory capability/flow coverage: missing or expired engine report, absent required read evidence, no verified write evidence, unregistered participation, unknown consumption, missing schedule anchor/first actual run, or unavailable adapter. Every cell includes a reason listing its dimensions. Write with no history is UNVERIFIED, not FAILED. A broken independent collector does not stop the other collectors.

11. **CRM connectivity.** Existing authenticated GET `/api/decision-engine/organizations` establishes API availability, with a cached source verification timestamp. Existing tenant-scoped context GETs establish API/database-backed table access. Frontend rendering is neither requested nor used as database health. Monitor access is explicitly separate from engine credential/network access. There is no existing bounded standalone CRM dependency-health API in the inspected deployment, so none was invented.

12. **Supabase connectivity.** Existing PostgREST GET `/rest/v1/organizations?select=id&limit=1` with the configured monitor key, or PostgreSQL `SELECT 1` using the existing read-only session/statement timeout. Empty SELECT responses are valid. A 42501 response proves the database answered but monitor table permission failed; it says nothing about engine permissions. `SELECT 1` alone does not verify tables/schema/RLS. CRM's successful scoped table reads can prove its own DB-backed capability even when the independent anonymous monitor role is denied. No frontend HTTP 200 is substituted for this check.

13. **Read capability.** For CRM, every registered required table must be present as an array in fresh, tenant-validated context for every configured organization. Empty arrays count as successful reads. Other engines require an explicit fresh `service_capabilities` report from their existing configured health URL, naming each required input and all monitored organizations. Generic health status and the monitor's CRM credential do not prove these engine permissions. Historical `read_succeeded` receipts show source activity/handoff evidence; they do not silently become a current read probe. Failure, unavailable and unknown remain distinct.

14. **Write capability without fake data.** Real attributable CRM records and explicit `write_persisted` trace receipts verify each registered output in every monitored organization within `write_evidence_seconds` (default 86,400). This is a write-evidence validity window, not an activity schedule. A fresh scoped engine capability report may independently report VERIFIED, FAILED or UNVERIFIED. A recent explicit persistence failure remains FAILED absent a later same-tenant/table success receipt. No INSERT/UPDATE/DELETE/claim/retry/approval is sent to an operational source. Credentials/configuration alone never verify a write. Last actual source write remains visible after its capability evidence expires. Test flags, when exposed by source records, are shown; a test-mode persistence record is not presented as proof of production execution.

15. **Successful handoffs.** Producer → CRM requires an attributable real stored record or explicit persistence receipt. Receiver consumption requires a same-organization foreign-key reference or an explicit `read_succeeded` receipt with the same table and record ID. The actual Domain Merchant request-claim SQL moves the identified request to RUNNING, so its registered durable RUNNING/COMPLETED state also proves consumption before a result exists. Unapproved/cancelled work is not overdue pickup. Missing consumption with an explicit deadline is PENDING/LATE; without a deadline it is UNKNOWN. Any outstanding late/failed obligation wins over unrelated confirmed traffic. Every contributing item is inspectable.

16. **workflow_run_id.** Existing authoritative grouping and trace storage remain unchanged. Record-carried run IDs and organization IDs locate corresponding full workflow traces from handoff evidence. Structured write/read receipts preserve the existing run ID. An ID or two completed stages alone do not prove an artifact crossed a boundary. Artifact receipt events are excluded from stage transition projection, so a successful read cannot falsely complete a workflow stage.

17. **Artifact lineage.** `recommendation_evidence.intelligence_report_id` proves report use; `execution_requests.recommendation_id` attributes requests to the service; `execution_results.execution_request_id` proves execution consumption; `feedback_evaluations.execution_result_id` proves feedback consumption. Existing trace enrichment continues following report, previous report, recommendation, request, result, prediction and feedback links. Explicit service identity wins over legacy type inference. Tenant mismatches and conflicting service identities are rejected. Correlation IDs remain available in traces; their possible reuse across cycles prevents treating them as unique workflow IDs. Timestamp proximity never establishes lineage.

18. **Schedule-aware health.** Optional registry engine `activity` or `trace_thresholds.{service}.{engine}.activity` accepts `expected_interval` seconds, `anchor_at` with UTC offset and `late_threshold` grace seconds. Without an anchor, a known authoritative actual run anchors the interval; without either, first due time stays unknown. The UI displays last expected, last actual, next expected and lateness beyond grace. Existing `expected_activity_seconds` is supported as an interval fallback. Existing per-stage `stalled_seconds` rules remain, including approval-wait exemption. This is a fixed-interval schedule; timezone-aware cron/calendar/DST rules are not implemented or guessed. No default daily schedule was inferred from the existence of a daily script.

19. **Normal idle versus stopped work.** Explicit no-work-due plus verified capability produces IDLE. A missed configured run, overdue configured handoff or existing configured stage stall produces DEGRADED. Unknown schedules do not penalize inactivity. Approval remains WAITING rather than becoming a timed-out business failure.

20. **Old timestamps.** Historical last activity/success/read/write/handoff remain visible. Source event time and dsmonitor observation time are separate. Old success never overrides a current outage, permission failure or unresolved workflow failure. Old write evidence can expire without converting it to a failed write. A cache hit retains the original verification timestamp.

21. **Refresh frequency.** Default UI/collector refresh remains 10 seconds. Local process checks and configured engine health URLs run each collector pass. CRM organization/API and independent Supabase checks cache for 60 seconds (`capability_seconds`); engine reports must be no older than that and cover the monitored organizations. CRM historical context stays at 120 seconds. Snapshot cadence remains 120 seconds. Open service/edge dialogs refresh from the existing UI polling state without triggering extra database queries.

22. **Caches.** CRM API organization results and Supabase probe results: 60 seconds; per-organization CRM context: 120 seconds. Capabilities preserve source `checked_at`; cached probes preserve `observed_at`. Workflow history remains in existing trace/snapshot infrastructure; schedule/health derivation is local each pass. No per-browser operational probes are added. A failure after a successful cached probe can take up to its TTL plus collection time to appear.

23. **Exact remote query surface.** GET CRM `/api/decision-engine/organizations`; GET `/api/decision-engine/context?organization_id=<allowlisted UUID>`; GET `/api/bot/feedback-loop/context?organization_id=<allowlisted UUID>`; GET Supabase `/rest/v1/organizations?select=id&limit=1` OR PostgreSQL read-only `SELECT 1`; optional existing configured engine health URL GETs. Existing read-only orchestrator stage/workflow queries are unchanged. No operational POST is issued. The two CRM context routes internally SELECT their existing tenant tables, including intelligence, predictions, recommendations, evidence, requests, results and feedback.

24. **Database load and limits.** This upgrade adds no per-cell/per-edge remote requests. Supabase performs one bounded row probe per TTL. CRM's inspected context routes paginate internally through all tenant records; a client `limit` would not constrain those existing endpoints. They remain expensive history reads, cached at 120 seconds, with the existing 4 MB response cap, request timeout, organization allowlist (max 20), trace limit (default 1,000) and local retention. CRM organizations also internally enumerates organizations; it is now cached instead of repeated every browser interval. A future bounded server-side capability endpoint would improve this further; this monitor-only upgrade does not claim that existing server-side pagination is bounded by the client response cap.

25. **UI evidence.** Services overview adds status counts and pipeline problems above the retained matrix. Cell details separate Current capability, dependency probe scope, Data flow, Recent activity/source times, Workflow and Evidence. Reasons, table/record IDs, organization scope, original verification times, failed/latest traces, engine/service explorers and observed history are visible. Pipeline edges open their individual evidence and trace links. Existing visual components and escaping are reused. NOT_CONFIGURED does not count as a failure.

26. **History/recovery.** An additive local SQLite `service_health_history` table stores observed status transitions for each service/engine, once per change, using the existing retention period. Full health projections are also included in existing periodic snapshots. Cell details expose the latest 20 transitions. Entering HEALTHY/IDLE after retained FAILED/DEGRADED/DISCONNECTED records displays the observed recovery time and prior reason. UNKNOWN is not recovery. Restarting the monitor preserves this history. Observation time cannot establish the exact earlier instant a source recovered.

27. **Registry updates.** Domain Merchant now has actual shared-loop input/output/dependency metadata and six handoffs with explicit phase metadata; no fabricated schedule/deadline. `devspace_services` now recognizes partial CRM/DevSpace One legacy outreach participation: `domain-exists` reads leads and `/api/ingest` persists companies/contacts/leads. Its evidence contract does not falsely substitute domain execution_results for legacy outreach outputs. The loop context does not expose these outreach records, so its ingestion edge stays UNKNOWN without source receipts. Existing aliases and ordered trace stages remain intact. Other absent implementations were not enabled merely to change badge colors.

DevSpace Services: partial CRM and DevSpace One outreach, not the complete declared lifecycle. Scholarship Research, DevSpace Clients and Investor Research: no implemented monitored service-engine path established. `dsorchestrator/workflows/{devspace_services,crm_companies}.py` explicitly declare unavailable business adapters; CRM migration 019 lists the corresponding catalog entries disabled. Generic CRM customer storage/UI and other Decision Engine strategies do not by themselves prove these canonical workflows are implemented. The architecture catalog and same-tenant source records were inspected in addition to the older trace report; no declaration was mistaken for an executable adapter.

29. **Currently proven handoffs.** Live scoped Domain Merchant intelligence records prove MMonolith → CRM persistence. This is historical real persistence, not proof of current MMonolith access. The verification artifact exposes the source IDs and source/observation timestamps. No successful full production cycle was fabricated or launched.

Decision Engine → CRM lacks an attributable domain recommendation persistence record in this scope. CRM → DevSpace One lacks a verified approved/claimed request; DevSpace One → CRM lacks a result; CRM → MMonolith lacks a feedback/result reference. Existing NO_ACTION/uncorrelated decision observations are not attached to reports by time. DevSpace Services lacks exposed legacy lead ingestion receipts; it was checked as the second partial implementation, but its business flow cannot be proven from the current context. Fresh scoped engine capability endpoints/reports and explicit write/read receipts are not installed by this monitor change. Without them, engine-scoped read/connectivity may remain UNKNOWN even when the monitor can reach CRM. Full live reliability remains unverified until real traffic exposes this evidence.

34. **Manual verification.** Run `venv/bin/python -m pytest -q`. Run `venv/bin/python scripts/verify_service_health.py` with normal network access for a read-only current diagnosis; it creates/removes only a temporary monitoring database and writes the report JSON. Optional engine health response (from an actual engine-owned safe diagnostic endpoint configured in `DSMONITOR_HEALTH_URLS`; this example is a contract, not a claimed deployed endpoint):

```json
{
  "status": "healthy",
  "service_capabilities": {
    "domain_merchant": {
      "checked_at": "2026-09-25T12:00:00Z",
      "organization_ids": ["<configured-organization-uuid>"],
      "connectivity_status": "CONNECTED",
      "reads": {"execution_requests": {"status": "VERIFIED", "reason": "Authorized scoped query succeeded; zero rows"}},
      "write_status": "UNVERIFIED",
      "work_expected": false,
      "reason": "CRM reached using this engine's configured identity"
    }
  }
}
```

`write_status:VERIFIED` must come from real persistence or trustworthy nonmutating capability information, never a fake production write. `checked_at` must be the actual check time, not merely a cached endpoint response time. Reports must cover every monitor-configured organization; incomplete scope is UNKNOWN. Missing input entries remain UNKNOWN. The monitor does not install this endpoint in another application.
