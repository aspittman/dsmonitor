# dsmonitor trace upgrade — 2026-09-22

The existing Flask application, interface, process monitoring, adapters, security boundary and SQLite database were extended in place. The monitoring implementation is tested; **full production end-to-end traceability has not been established**. Existing records lack complete correlation, and several requested workflows are not implemented. No synthetic runs were inserted into live monitoring storage. Business engines were not executed, restarted, modified or deployed.

1. **Actual domain_merchant path.** `dsorchestrator/workflows/domains.py` and `core/workflow.py` declare research (MMonolith) → decision (Decision Engine) → approval (CRM) → execution (DevSpace One) → feedback (MMonolith) → updated_intelligence (MMonolith) → redecision (Decision Engine). dsorchestrator coordinates this sequence; it has no independent dispatch stage declaration. CRM persists the reference-linked artifacts. `engines/bridge.py` explicitly restricts execution to test investigations. Separately, `dsmonitor/scripts/domain_daily.py` runs MMonolith feedback and research discovery, Decision Engine scheduled review, then DevSpace One Afternic sync/Apollo preparation/delivery jobs. Those independent invocations are not a demonstrated single workflow. The inspected live source database contains zero orchestrator runs.

2. **Actual scholarship_research path.** No implemented DevSpace path was found. Neither `scholarship_research` nor `scholorship_research` was present in the inspected engine code/configuration. Existing monitor `scholarship` remains compatible; the new explorer reserves `scholarship_research` as NOT CONFIGURED. Schopath's Scout contract describes a separate system. No spelling in a source engine was changed. A deployment using another spelling can register that identifier or an explicit alias.

3. **Actual devspace_services path.** `dsorchestrator/workflows/devspace_services.py` declares a lifecycle but says its business adapters are not implemented. DevSpace One has discovery → website auditing → opportunity scoring → review-ready drafting → CRM ingestion in its outreach implementation. This is not evidence that all engines process `devspace_services` end to end. The registry therefore has no asserted cross-engine stage path for this service. Existing `devspace-services` compatibility is preserved.

4. **Actual devspace_clients path.** `crm-companies` is an organization-scoped orchestrator declaration whose business adapters are not implemented. There is no verified complete path. The existing monitor identifier `crm_business` and operational identifier `crm-companies` map to the explorer's `devspace_clients` label without changing source identifiers. Arbitrary CRM recommendations are no longer automatically misclassified as client work.

5. **Existing identifiers.** dsorchestrator already has `workflow_runs.id`, `stage_runs.workflow_run_id`, stage IDs, attempts and `correlation_id`; its job payload already propagates `workflow_run_id`. MMonolith domain reports have `run_key`, report IDs, `correlation_id` and previous-report links. Decision Engine has decision-run IDs, recommendation IDs, report evidence, and correlation IDs inside domain recommendation parameters. CRM stores the report/recommendation/request/result/feedback foreign keys. DevSpace One execution uses request/result IDs. Correlation can persist across feedback generations, so it is not treated as a unique workflow execution ID.

6. **workflow_run_id instrumentation.** Existing orchestrator IDs are reused. No new operational IDs were installed in any source system. An optional dependency-free `services/trace_emitter.py` helper and structured JSONL adapter were added. The helper can create context at the work-creation boundary or accept an existing ID; the same context must be carried across boundaries and retries. It is **not wired into source engines**, so it does not close the instrumentation gap for independent cron invocations. Context passed to JSONL ingestion retains parent and correlation identifiers. Workflow completion requires an explicit completion event. A local trace key is a monitoring storage key, not a competing operational run ID.

7. **MMonolith changes.** None to the engine. Its existing local research-store monitoring remains. CRM report records now also appear as research fragments even without a recommendation. A stored report establishes research artifact existence; it does not establish downstream receipt or workflow completion.

8. **Decision Engine changes.** None to the engine. Its dsmonitor adapter now reads the existing structured daily decision log using explicit DOMAIN_ACQUISITION strategy fields and decision-run IDs. It does not attribute all strategies in an organization-wide decision to Domain Merchant. Undated events remain undated; policy rejection is not a failure. No evaluation is linked to a research report using timing guesses.

9. **DevSpace CRM changes.** None to the engine or deployed API. Existing authenticated, organization-scoped context APIs are reused. Monitor-side normalization now preserves unlinked reports and recognizes NO_ACTION as SKIPPED rather than waiting for approval. Unknown execution services retain their source identifier; absent service attribution is `unknown_service`.

10. **dsorchestrator changes.** None to the engine. Its monitor adapter now retains actual attempt numbers and source stage IDs. All existing operational tables are opened read-only. Its zero-row database was not populated with test evidence.

11. **DevSpace One changes.** None to the engine. Existing process/log monitoring and explicit CRM request/result links remain available. Generic JSONL ingestion can receive future engine instrumentation, but no new producer was installed. Existing execution restrictions were preserved.

12. **Workflow Trace Explorer.** A major navigation item lists retained authoritative runs and legacy fragments. Filters cover service, engine, organization, status, stage, failed engine, failed stage and start-time range. Search covers run/source IDs, correlation, service, organization name/ID and observed error text. Details show current location, last successful stage, cut-off, expected/observed stages, attempts, source references, timeline and timing. `GET /api/traces` and `/api/traces/<trace_id>` expose the same normalized monitoring data. Default retained view is bounded to 1,000 runs; it is not exhaustive ecosystem history.

13. **Engine Trace Explorer.** Engines navigation includes MMonolith, Decision Engine, CRM, dsorchestrator and DevSpace One. Existing engine detail dialogs also link to their explorer. Selecting a service shows engine-specific recent runs, errors, events, last success, failures and observed duration. Selecting a run opens engine-scoped evidence with a link to its complete workflow trace. Service selection provides the inverse cross-engine view.

14. **Matrix status.** Every Service × Engine cell is clickable. It considers observed stages for that service and engine, chooses current failure/stall evidence within a run, and orders run observations by source activity. Latest observed completion is HEALTHY only with a source timestamp; undated completion is UNKNOWN. An outstanding configured stall is STALLED. A configured expected activity interval can produce DEGRADED. NOT CONFIGURED, NO DATA and NOT REACHED remain separate. Process/API availability is displayed independently. Counts are bounded observations, not daily ecosystem totals; retry-attempt failures are retained separately from final run failures.

15. **Cut-off detection.** The first unresolved failed stage in the registered sequence is the root stage. Earlier completed stages provide the last success. If an authoritative orchestrator workflow reports failure without a failed engine stage, the failure is attributed to coordination at its recorded current stage, with the actual workflow error. Unknown paths are not expanded into an invented sequence. Stage paths in this implementation are ordered sequential expectations; arbitrary DAG dependency evaluation is not implemented.

16. **NOT REACHED versus FAILED.** Expected downstream stages with no execution evidence become NOT REACHED only after a known cut-off in an asserted path. Upstream gaps remain NOT STARTED. Observed downstream stages are not overwritten merely because an upstream failure exists. Legacy fragments have no asserted full path, so missing remote records are not called NOT REACHED. A root failure contributes one failed workflow to the summary; downstream absence contributes zero failures.

17. **WAITING versus STALLED.** WAITING_FOR_APPROVAL never ages into STALLED. RUNNING requires an explicit service/engine/stage `stalled_seconds` threshold and an activity timestamp. Ordinary WAITING additionally requires `stall_waiting: true`. Defaults do not guess thresholds. Details show expected duration, inactivity, elapsed stage time where known, and threshold. No retry is initiated. Existing process-view STALE behavior remains backward compatible; new trace logic independently uses the original source state.

18. **Retries.** Attempts are grouped under the same workflow and stage. Last-attempt state determines current stage state; earlier errors remain visible. A successful later attempt displays COMPLETED AFTER RETRY. If old attempts were overwritten before dsmonitor observed them, their error details cannot be reconstructed. Independent retry IDs can be linked by explicit `parent_run_id` context; no such links are guessed.

19. **Root failures.** Engine, service, run and stage attribution derives from source stage records or explicit event context. Historical failed attempts followed by success do not count as unresolved root failures. The summary counts authoritative failed workflows once. A generic uncorrelated log error is not attached to a nearby run. Existing error feeds link to the matching full trace where a source run ID is available.

20. **Durations.** Total duration requires actual workflow start and completion timestamps. Stage durations come from recorded source start/end values. Per-engine execution totals sum available non-approval durations, including observed retry attempts. Approval intervals are displayed separately when available. Missing intervals, undated log entries and human approval duration are not estimated. Totals are labeled observed; partial coverage is not presented as complete performance measurement. Parallel/custom stages could overlap, so their summed execution time is not wall-clock duration.

21. **Engine/service health.** Existing engine process, API, heartbeat, dependency and log health checks remain. Latest observed service failures or configured stalls add an explained DEGRADED check while preserving engine availability. Matrix details show independent process/API availability. Recent successes, consecutive observed failures, stalls and explicitly configured expected frequency contribute evidence. Infrequent services have no default inactivity penalty. This is an explainable bounded-evidence policy, not a statistically complete success rate or scheduling-aware SLA implementation.

SQLite stores sanitized monitoring projections, never operational truth.

Stalls are threshold-based indications, not proof that a worker is dead. NO_ACTION lacks a specific service identity and is not called client work. The decision log lacks timestamps and does not expose the report-to-decision input lineage needed to connect it to one report. Source context APIs do not expose a complete decision-run ledger. 24. **Legacy display.** CRM fragments and structured decision observations without a reliable workflow ID display LEGACY / UNCORRELATED. They retain source IDs, any existing correlation, stages, errors and references. They do not enter authoritative workflow totals. A fragment with a completed research stage can correctly have UNKNOWN workflow status. Fragment observations may overlap historical business evidence; their engine-level counts are not unique ecosystem workflow counts.
